## 1. 🎯 GraphView（關聯圖譜）

### 1.1 它是什麼、解決什麼問題

一般的檔案總管是**樹狀結構**：一個檔案只能待在一個資料夾裡。但同一個專案的檔案，常常散落在「下載」、「學校」、「桌面」三個不同的地方。

GraphView 把「**檔案**」和「**標籤／分類**」都畫成節點（node），檔案帶有某個標籤，就在兩者之間畫一條線（edge）。這樣一來，散在不同資料夾、但有共同標籤的檔案，會被同一個分類節點拉在一起。這些跨資料夾的關聯，在樹狀檢視裡是看不到的。

> 口試定位：GraphView 是「**探索**」工具，不是日常操作工具。它的任務是讓使用者發現跨資料夾的意外關聯。

### 1.2 技術基礎（初學者版）

Qt 有一套 **Graphics View Framework**，包含三個角色：

| 角色 | Qt 類別 | 比喻 | 在我們專案裡 |
|---|---|---|---|
| 場景 | `QGraphicsScene` | 一大張畫布（可以超大） | 24000×24000 的虛擬畫布 |
| 物件 | `QGraphicsItem` | 畫布上的貼紙 | `Node`（檔案／標籤）、`Edge`（連線） |
| 視窗 | `QGraphicsView` | 看畫布的鏡頭（可縮放、平移） | `GraphWidget` |

### 1.3 程式結構（`src/gui/GraphWidget.h`）

- **`Node`**（繼承 `QGraphicsItem`）：分 `File` 和 `Tag` 兩種。寬度會依文字長度動態計算（`updateDimensions()` 用 `QFontMetrics` 量字寬，避免文字被截斷）。另外有出現時的彈跳動畫（`beginAppearPop` / `tickAppearPop`）
- **`Edge`**（繼承 `QGraphicsItem`）：連接兩個 Node，每個分類有自己的顏色（`edgeColorForTag`）
- **`GraphWidget`**（繼承 `QGraphicsView`）：負責建圖、縮放、平移、篩選面板和工具列

### 1.4 建圖流程（`GraphWidget::buildGraph()`，GraphWidget.cpp:1185）

```
1. 清空場景
2. 讀使用者在篩選面板勾選的條件
   ├─ 系統標籤（副檔名分類等）
   └─ AI 抽屜分類（18 大類，前綴 SF_DRAWER:）
3. 找出符合條件的候選檔案
   └─ 嚴格限制在目前工作區內（sfAbsolutePathUnderWorkspaceRoot），不會跨工作區洩漏
4. 建「分類節點」：顯示成 "(檔案數) 分類名"
   └─ 重點：不是每個 AI 小標籤都建節點，而是收斂到 18 個抽屜，避免節點爆炸
5. 建「檔案節點」+ 連線到它所屬的分類節點
6. 每建一個節點都檢查上限 m_maxGraphNodes（預設 50，可調 10～500）
7. fitAllNodes()：自動縮放到所有節點都看得見
8. runAppearPopAnimation()：節點彈出動畫
```

### 1.5 版面演算法的演進（口試亮點）

**初版（2025-12，init commit）：力導向佈局（Force-Directed Layout）**

```cpp
// 初版 Node::calculateForces()
// 所有節點互相排斥（像同極磁鐵）
xvel += (dx * 150.0) / l;
// 有連線的節點互相吸引（像彈簧）
double weight = (edgeList.size() + 1) * 10;
```

每個 timer tick 都會重新算一次力、移動一次節點，直到畫面穩定下來。

**問題**：節點一多就會**互相重疊**、一直抖動停不下來，計算量是 O(n²)。

**現版（2026-05-15，Sprint 13.20–13.24）：靜態螺旋尋址（Spiral Search）**

```cpp
// GraphWidget.cpp:1119 placeNodeWithSpiral()
// 從中心開始，沿著螺旋往外找第一個「沒有東西」的空位
for (step = 0; !placed && step < 12000; ++step) {
    x = center.x() + radius * cos(angle);
    y = center.y() + radius * sin(angle);
    if (scene()->items(proposedRect, ...).isEmpty()) { placed = true; break; }
    angle += 30° + 隨機抖動(-5～+5°);
    if (angle >= 360°) { angle -= 360°; radius += radiusStep; }  // 繞完一圈，半徑變大
}
```

- 每個節點都會加 20px margin 再做碰撞檢查，所以**保證不重疊**
- 力導向已經關掉了：`Node::calculateForces()` 現在直接 `newPos = pos(); return;`
- 加上隨機起始角度和抖動，避免節點排得像死板的同心圓

> 口試可以說：「我們一開始用物理模擬，但在真實資料量下會重疊又停不下來，所以改成確定性的螺旋尋址演算法，用碰撞檢測保證 100% 不重疊。」

### 2.3 預覽區細節

- **圖片預覽**：自訂的 `ScaledPreviewImageLabel`（MainWindow.cpp:~640-680），保存原圖 `m_source`，每次視窗縮放（`resizeEvent`）就用 `Qt::KeepAspectRatio + SmoothTransformation` 重新等比縮放。用 MIME 判斷 `image/*` 才走這條路
- **文字預覽**：PDF 用 `DocumentParser::extractPdfText`，其他格式各自抽文字。用 `QStackedWidget`（`m_previewBodyStack`）在圖片和文字之間切換
- **分頁化預覽**（Sprint UI 打磨）：個人標籤、AI 建議、AI 摘要收進同一個 TabWidget，高度鎖 104px，防止版面跳動
- **打字機動畫**：摘要以 30ms/字逐字出現（後來改成可關閉的選項）
- **關鍵字黃色高亮**：搜尋時以 HTML 高亮摘要裡的關鍵字
- **旋轉載入動畫**：自訂 `FileItemDelegate`，用 `kSpinRole` 狀態加上 50ms Timer 在清單項目上畫 BusyChip
- **低信心標示**：只能讀 metadata、或內容太少的檔案會被放進 `m_lowConfidencePaths`，UI 上會標示出來

### 2.4 重要教訓：預覽和分析要分開（Sprint 13.44）

曾經為了效能，讓「已經分析過的檔案」跳過文字抽取，結果**預覽區也跟著不顯示原文**，只剩 AI 摘要。後來緊急回滾，原則改成：**預覽永遠抽真實文字；只有 AI 分析路徑才能吃快取。**

## 3. 🎯 第二個語言模型：Embedding 語意檢索

### 3.1 初學者版：為什麼需要「第二個」模型？

我們有兩種 AI 模型，各自擅長不同的事：

| | 聊天模型（第一個） | Embedding 模型（第二個） |
|---|---|---|
| 模型 | Llama-3.1-8B / Qwen2.5-3B | **BGE-M3**（約 440 MB） |
| 擅長 | **生成**文字：寫摘要、想標籤 | **比較**意思：把一段文字變成一組數字（向量） |
| 比喻 | 會寫作文的學生 | 會把每本書放到地圖上座標的圖書館員 |
| 速度 | 每個檔案 10～20 秒 | 每段文字幾十毫秒 |

**Embedding（向量）是什麼？** 把一段文字轉成一長串數字，例如 1024 個數字，可以想成這段文字在「意義空間」中的座標。意思相近的文字，座標就靠得近。搜尋時只要把查詢也轉成座標，再找最近的幾個檔案就好。

### 3.2 演進：從「用聊天模型硬搜」到「專用 embedding 模型」

#### 第一代（2026-05-12 ～ 05-13）：讓聊天模型當檢索器

```
把工作區檔案的摘要配上編號 → 塞進 prompt：
  [1] 報稅單.pdf：2023 年綜所稅申報...
  [2] 旅遊行程.md：日本 5 日遊...
  ...
問模型：「使用者要找『去年的稅』，哪些編號相關？只回傳整數陣列」
模型回：[1]
```

一路上遇到的問題和解法：

| 問題 | 解法 | 出處 |
|---|---|---|
| 模型回傳的檔案路徑格式亂七八糟，匹配率 0% | **ID 映射檢索**：不讓模型處理路徑，只回整數 ID | 11.4–11.6，`9651fe6` |
| 塞超過 180 筆摘要時超過 10,000 tokens，macOS 直接把程式殺掉（OOM） | 硬性上限：**最多 30 個檔案**，加上 context 長度檢查 | 11.9，`65aa862` |
| 模型輸出壞掉的 JSON，搜尋結果空白 | **雙擎混合檢索**：LLM 失敗時，C++ 自動改用關鍵字比對兜底 | 11.15 |
| 「找照片」這種查詢，丟給 LLM 很浪費 | **意圖路由**：命中「照片」就直接比對 png/jpg，完全不呼叫 LLM | 11.22，`4101133` |
| 搜尋時掃描磁碟造成 UI 卡住 | 整條流程移到 `QtConcurrent::run` 背景執行 | 11.21，`d2c31e6` |

**第一代的根本限制**：聊天模型不是設計來比較相似度的，而且 context window 有限，**最多只能看 30 個檔案**。

#### 🎯 第二代（2026-06-11，`25232b5`）：加入專用 Embedding 模型

**`EmbeddingEngine`**（`src/ai/EmbeddingEngine.cpp`）：

```cpp
llama_context_params cp = llama_context_default_params();
cp.embeddings  = true;                            // 告訴 llama.cpp：要的是向量，不是生成文字
cp.n_ctx       = 2048;
cp.pooling_type = LLAMA_POOLING_TYPE_UNSPECIFIED; // 依 GGUF 檔內設定（BGE 用 CLS pooling）
```

`embedText()` 的流程：

```
文字 → tokenize → 超過 2040 tokens 就截斷 → 清記憶體 → llama_decode
     → llama_get_embeddings_seq() 取得句向量（拿不到就改取最後一個 token 的向量）
     → L2 正規化（除以向量長度，讓長度變成 1）
```

**為什麼要做 L2 正規化？** 正規化之後，兩個向量的「**內積**」就等於「**餘弦相似度**」，計算最省事：

```cpp
float EmbeddingEngine::similarity(a, b) {  // 就是 Σ a[i]*b[i]
```

**搜尋流程**（`sfRunEmbeddingSemanticSearch`，MainWindow.cpp:7755）：

```
1. 查詢文字 → 向量
2. 走過工作區每個可分析的檔案：
   ├─ 用 content hash 當索引 key（沒有 hash 就用 "p:"+路徑）
   ├─ 索引裡已經有向量 → 直接用
   └─ 沒有 → 用「檔名 + 標籤 + 摘要前 400 字」算向量（每次最多新算 800 個）
3. 每個檔案和查詢算相似度 → 由高到低排序
4. 取前 30 名（kTopK）
   └─ 前 3 名一定顯示；第 4 名之後，相似度要 ≥ 0.35 才顯示（kSimilarityFloor）
5. 新算的向量存回 .smartfile/embeddings.bin（QDataStream 二進位格式）
```

**設計重點**：

| 設計 | 原因 |
|---|---|
| 用 **content hash** 當 key | 檔案改名或搬移時向量還在，不用重算；內容相同的檔案共用一個向量 |
| **查詢時惰性建立** + 每次上限 800 | 第一次搜尋不會卡太久；索引隨使用次數累積（todo：之後改成分析完成就順便建） |
| 「前 3 名一定顯示」 | 就算相似度都偏低，也不會給使用者一片空白 |
| 背景執行 + **Workspace Epoch** 檢查 | 搜尋途中切換工作區，舊結果會被丟掉，不會寫錯地方 |
| 保留第一代當 **fallback** | 使用者沒下載 embedding 模型時，系統還是能用 |
| 模型下載器加了 BGE-M3 勾選框 | `ModelDownloadDialog.cpp`，大小 <300MB 會判定下載不完整 |

> 口試一句話：「聊天模型擅長寫，不擅長比；我們加入專用 embedding 模型，把語意搜尋從『最多看 30 個檔案』變成『全工作區、不限數量』，而且向量用內容雜湊快取，跨次啟動持續累積。」

### 3.3 誠實的限制

- **還沒做 precision / recall 的量化評測**，目前只做定性展示（口試 Q5）
- 線性掃描所有向量，複雜度 O(n)；超過 10 萬個檔案時要考慮 ANN 索引（例如 HNSW），已列在 todo
- 每個檔案的向量只看「檔名 + 標籤 + 摘要」，不是全文

## 4. LlamaEngine：初學者解釋 + 我們做了什麼

### 4.1 初學者版：LlamaEngine 是什麼？

`LlamaEngine` 是我們自己包的一層「**AI 管家**」。底下真正做數學運算的是 llama.cpp，但 llama.cpp 的 API 很原始（要自己切 token、管記憶體、一個字一個字生成），所以我們包了一層，讓主程式只要呼叫：

```cpp
std::string json = llamaEngine.suggestTags(檔名, 內容, ...);
// 回傳：{"summary": "...", "tags": ["...", "..."]}
```

**語言模型怎麼「寫字」？（核心觀念）**

1. 先把文字切成 **token**（字詞碎片），例如「作業系統」可能被切成 2～3 個 token
2. 模型讀完前面所有 token，對**詞彙表裡每個 token** 打分數：「下一個最可能是什麼」
3. 挑一個 token 接上去，然後重複第 2 步
4. 直到模型輸出「結束」token，或達到長度上限

**KV Cache 是什麼？** 模型讀過的內容會被記在 KV Cache 裡，就像短期記憶，下一個字不用從頭重讀。但這也代表：**分析完 A 檔案不清掉的話，B 檔案會殘留 A 的記憶**。

**量化（Q4_K_M）是什麼？** 模型的參數原本是高精度浮點數，量化就是把每個參數壓縮成大約 4 bit 來存。8B 模型因此可以從約 16GB 壓到 5GB 以內，品質損失不大，才能在筆電上跑。

### 4.2 LlamaEngine 的生命週期（`src/ai/LlamaEngine.cpp`）

```
建構：llama_backend_init()；建立 3 分鐘的 idleTimer
   │
loadModel(path)
   ├─ 檔案小於 100MB → 拒絕（下載不完整的模型會讓 GGML 崩潰）
   └─ ensureModelLoaded()
        ├─ n_gpu_layers = 100   → 全部層丟給 GPU（Mac 上就是 Metal）
        ├─ n_ctx = 8192         → 一次最多讀 8192 tokens
        ├─ n_batch = 2048
        └─ n_threads = 從設定讀（使用者可熱切換 CPU 執行緒數）
   │
每次推論：InferenceGuard（RAII）
   ├─ 進入：上鎖 + 活躍推論數 +1 + 暫停 idleTimer
   └─ 離開：活躍推論數 -1 + 解鎖 + 重新開始 3 分鐘倒數
   │
閒置 3 分鐘 → unloadModel()
   ├─ 如果還有推論在跑 → 延後卸載
   └─ llama_free + llama_model_free → RAM 釋放
   │
下次要用 → ensureModelLoaded() 自動重新載入（Lazy Loading）
```

### 4.3 一次推論的完整流程（`generateResponseImpl`，LlamaEngine.cpp:242）

| 步驟 | 程式 | 為什麼 |
|---|---|---|
| 0. 檢查取消 | `m_cancelFlag` | 使用者按停止或切換工作區時要立刻收手 |
| 1. 套用執行緒數 | `llama_set_n_threads` | 設定面板調整後立即生效 |
| 2. **清 KV Cache** | `llama_kv_cache_clear` + `llama_memory_seq_rm`，離開時再清一次（RAII） | 防止上一個檔案的記憶汙染這一次 |
| 3. Tokenize | `llama_tokenize` | 文字 → token |
| 4. 長度防護 | prompt 必須 ≤ `n_ctx - 200`，否則回傳 `"Error: Prompt length exceeds context window"` | 保留 200 tokens 給生成；超長直接拒絕，不盲目截斷（11.10 的教訓） |
| 5. 讀入 prompt | `llama_decode(batch)` | 模型一次讀完整段 prompt |
| 6. 建取樣器鏈 | Grammar sampler（GBNF）→ Greedy sampler | 見 §6 |
| 7. 逐 token 生成 | 迴圈最多 `maxNewTokens` 次；每輪檢查取消、遇到結束 token 就停 | 硬上限：保證幾秒內一定返回，不會無限生成 |
| 8. 轉回文字 | `llama_token_to_piece` | token → 文字 |

### 4.4 `suggestTags` 的三條 prompt 分支（`suggestTagsImpl`）

| 分支 | 觸發條件 | 摘要怎麼來 | 標籤怎麼來 |

**為什麼摘要要寫死固定文字？** 防幻覺（Sprint 6.2）。讀不到內容時，模型會根據檔名「瞎掰」一段摘要，把固定文字寫死在 prompt 裡，就能讓它不亂編。

## 5. 多種檔案格式是怎麼支援的

### 5.1 核心觀念

我們的分析是「**抽出文字 → 給 LLM 讀**」，所以每種格式要解決的問題都是：**怎麼從這個檔案拿到乾淨的純文字？** 拿不到文字的（例如照片），就退而求其次，拿 **metadata（檔案的屬性資訊）**。

總入口：`DocumentParser::extractTextForAi()`（`src/core/DocumentParser.cpp:616`）

### 5.2 格式總表

| 類別 | 副檔名 | 怎麼抽 | 備註 |
|---|---|---|---|
| 日常純文字 | `txt` `md` `csv` | 直接讀 UTF-8 | 背景會自動分析 |
| 開發／重型文字 | `sql` `db` `json` `xml` `py` `cpp` `js` `ts` `html` `h` `c` `hpp` `log` `yaml` `ini`... | 直接讀 | **只有手動點選才分析**，背景爬蟲不碰（雙層白名單，Sprint 11.12） |
| Word | `docx` `docm` `dotx` `dotm` | 解 ZIP → `word/document.xml` → `QXmlStreamReader` 讀 `<w:t>` 文字節點 | |
| Excel | `xlsx` `xlsm` `xltx` `xltm` | 解 ZIP → `xl/sharedStrings.xml`（所有儲存格的共用字串）+ `sheet1.xml` | 巨集在 `vbaProject.bin`，我們完全不讀，所以**不受巨集影響** |
| PowerPoint | `pptx` `pptm` `potx` `potm` | 解 ZIP → 所有 `ppt/slides/*.xml` 和 `notesSlides/*.xml` → 用 regex 抓 `<a:t>...</a:t>` | 連講者備忘稿也一起讀 |
| OpenDocument | `odt` `ods` `odp` | 解 ZIP → `content.xml` → 清掉 XML 標籤 | |
| EPUB | `epub` | 解 ZIP → 所有 `.html` / `.xhtml` → 清掉標籤 | |
| PDF | `pdf` | `QPdfDocument`（等待載入最多 5 秒）讀**前 5 頁**；沒有就改用 Poppler；再沒有就用二進位啟發式；最後才退到 metadata | 四層 fallback |
| 舊版二進位 Office | `doc` `xls` `ppt` | **直接回傳空字串，不解析** | 舊格式不是 ZIP，硬解會崩潰（`7b78f9b`） |
| 圖片／影音／未知 | `jpg` `png` `mp4`... | **Metadata** | 見 5.5 |
| 系統／編譯產物 | `.DS_Store` `.dll`、`node_modules/` `build/` `venv/` | 直接略過，或標成 `[開發與系統檔]` | 不浪費算力 |

### 5.3 關鍵技術：Office 檔其實是 ZIP 壓縮檔

初學者可能不知道：`.docx`、`.xlsx`、`.pptx` 的副檔名改成 `.zip`，就能直接解壓縮，裡面是一堆 XML 檔。這個格式叫 **Office Open XML**。我們用 **miniz**（一個超小型的 C 語言 ZIP 函式庫，`CMakeLists.txt` 用 FetchContent 拉進來）在記憶體中解壓，取出需要的那幾個 XML。

```
報告.docx (ZIP)
├─ word/document.xml   ← 內文在這裡：<w:p><w:r><w:t>你好</w:t></w:r></w:p>
├─ word/styles.xml
└─ [Content_Types].xml
```

**XML 雜訊清洗**（`cleanseXmlTagNoise`，DocumentParser.cpp:38）：

```cpp
s.replace(QRegularExpression("<[^>]*>"), " ");  // 刪掉所有 <標籤>
s.replace(QRegularExpression("\\s+"), " ");       // 壓縮連續空白
```

> 為什麼需要清洗？Sprint 9.5 / 9.6 發現 PPTX 解出來帶著大量 `<a:pPr>` 這類標籤，直接送給 LLM 會造成 **token 爆炸**，模型也會開始幻覺。

### 5.4 PDF 的四層 fallback

```
1. QPdfDocument（Qt 官方）
   └─ 等 Status::Ready（最多 5 秒），只讀前 5 頁（kAiPdfMaxPages）
       ↓ 抽不到
2. Poppler（如果編譯時有裝 poppler-qt6）
       ↓ 抽不到
3. 二進位啟發式（extractPdfBinaryHeuristic）
   └─ 讀前 4MB，只保留連續 ≥4 個可列印 ASCII 字元的片段
       ↓ 還是抽不到（例如純掃描 PDF）
4. Metadata（pdfMetadataOnly = true）
```

**為什麼只讀前 5 頁？** 這是取捨：分類只需要「主題訊號」，通常前幾頁就看得出來。代價是極長的文件可能漏掉後面的細節（口試 Q4）。

### 5.5 🖼️ 照片／不可讀檔案：Metadata 分析（2026-06-18，`383ccfc`）

照片沒有文字層，所以改用 `DocumentParser::extractMetadataContext()`（DocumentParser.cpp:574）組出一段「屬性描述」給 LLM：

```
[此檔案無可擷取文字內容，以下為其中繼資料 (Metadata)]
檔名: 京都_清水寺_夜景.jpg
副檔名: jpg
MIME 類型: image/jpeg        ← QMimeDatabase 判斷（看檔案內容，不只看副檔名）
大小: 2048 KB
修改日期: 2025-11-02
所在資料夾: 日本旅遊2025      ← 資料夾名稱常常是很強的線索！
影像尺寸: 4032 x 3024 像素   ← QImageReader 只讀檔頭，不解碼整張圖，很快
```

然後走 LlamaEngine 的 **metadata-only 分支**：

- 摘要固定為「已讀取 Metadata 進行智能分類。」，**不讓模型假裝看過照片**
- 標籤只能依檔名、資料夾、屬性推測
- 這個檔案會被標成**低信心**（`m_lowConfidencePaths`），UI 會提示

> 口試說法：「我們不讓 AI 假裝看得懂照片。照片只用檔名、資料夾、尺寸、日期這些 metadata 做『保守分類』，並在 UI 標成低信心。讀圖片內容（OCR、多模態）是明確的未來工作。」
> ⚠️ 目前**沒有讀 EXIF**（拍攝時間、GPS），也**沒有 OCR**，被問到要誠實說。

### 5.6 抽出來之後：品質檢查 + 淨化

**低品質判斷**（`sfExtractLooksLowQuality`）：符合任一條件就改走 metadata

- 少於 12 個字
- 有意義字元（字母、數字、中文）佔比低於 25%（代表抽出來的是亂碼）
- Office 類檔案少於 24 個字

**淨化**（`sanitizeTextForAi`）：

- 刪除 `\0`（null byte）：這是 Sprint 13.1 讓 JSON parser 崩潰的元兇
- 刪除落單的 surrogate（壞掉的 emoji 或中文字半邊）
- 刪除控制字元，連續空白壓成一個

**長度控制**：

- PDF / docx / pptx：白名單 regex（只留中英數和常用標點）→ 取前 **800 字**
- 其他格式：截斷到 **1800 字**（`kAiTextMaxChars`），並加上「...[內容過長已截斷]」

**內容太少時的補強**（MainWindow.cpp:~8795）：少於 50 字，就在前面加上 `[Parent folder: xxx]`，後面加上大小和日期，並標成低信心。

## 6. GBNF 約束解碼

### 6.1 問題：LLM 吐出來的 JSON 常常是壞的

舊做法只能**事後補救**，演進過程如下：

| 時期 | 做法 | 問題 |
|---|---|---|
| Sprint 6.3 | Prompt 裡寫「只能輸出 JSON」+ regex `\{.*\}` 多段合併 | 模型照樣加 markdown、多逗號 |
| Sprint 9.15 | `extractFirstBalancedJsonObject`：括號深度解析，加上 500 次迴圈和 40 萬字元上限 | 只防得了崩潰，防不了格式錯 |
| 2026-05-15 `f817540` | 放寬嚴格 JSON，允許直接抓白話文摘要 | 治標 |
| Sprint 13.36–13.49 | 多層 fallback + **JSON 暴力剪刀**（從第一個 `{` 切到最後一個 `}`） | 還是事後補救 |
| **2026-06-11 `25232b5`** | **GBNF：生成的當下就限制** | ✅ 原始輸出 JSON 合法率實測 100% |

### 6.2 文法（`LlamaEngine.cpp:233`）

```
root   ::= "{" ws "\"summary\"" ws ":" ws string ws "," ws "\"tags\"" ws ":" ws tags ws "}"
tags   ::= "[" ws string (ws "," ws string)? (ws "," ws string)? ws "]"
string ::= "\"" char{1,300} "\""
char   ::= [^"\\\x00-\x1F] | "\\" (["\\/bfnrt] | "u" [0-9a-fA-F]{4})
ws     ::= [ \t\n]?
```

- `root`：key 的名稱和順序寫死，不可能拼錯，也不可能多出欄位
- `tags`：1 個必填 + 2 個選填，在**文法層**就限定 1～3 個標籤
- `string`：不能是空字串，最多 300 字
- `char`：排除引號、反斜線和 `\x00-\x1F` 控制字元，只允許合法的 JSON 跳脫
- `ws`：最多一個空白，不浪費 token

### 6.3 原理

```cpp
smpl = llama_sampler_chain_init(...);
llama_sampler_chain_add(smpl, llama_sampler_init_grammar(vocab, grammar, "root")); // ① 把違反文法的 token 機率設成 0
llama_sampler_chain_add(smpl, llama_sampler_init_greedy());                        // ② 在剩下的 token 裡挑最高分
```

比喻：不是讓學生隨便寫完再幫他擦錯字，而是給他一張**只能填在特定格子裡的答案卡**。

- **Greedy**：同一個檔案每次跑都得到一樣的結果，評估才可重現
- 文法解析失敗 → 降級為不受約束的解碼，舊的暴力剪刀仍然保底

### 6.4 兩層分工

- **GBNF 管語法**：保證輸出是合法 JSON
- **AiJsonSanitizer 管語意**：標籤去重、過濾被拒絕的標籤、每個標籤最多 15 字、摘要不可為空

### 6.5 100% 是怎麼量的

`sfo_eval` 讀的是 `lastRawSuggestTagsOutput()`，也就是**經過 sanitizer 之前**的原始輸出，再檢查能不能 parse 成物件、而且有 `summary` 欄位。如果量的是 sanitizer 之後的結果，100% 就沒有意義，因為 sanitizer 本來就保證輸出合法。

### 6.6 誠實的限制

- GBNF 只保證**語法**，不保證**內容**正確。標籤分得對不對，是分類正確率在量的
- GBNF 保證「每一步都不會走出文法」，但**不保證一定走完**：碰到 600 tokens 的上限，或使用者中途取消，輸出可能停在一半。實測 100% 是因為摘要通常很短，被截斷的情況則由 sanitizer 兜底

## 8. 重大 Bug 檔案（症狀 → 根因 → 解法）

> 口試 Q18「你們是不是用 AI 寫的？」→ 挑 2～3 個**親手 debug 的細節**來講最有說服力。⭐ 是最推薦的。

### ⭐ 8.1 台綜大事件：提示詞汙染（2026-05-09，`73ec77b`）

- **症狀**：連續分析不相關的檔案時，教師履歷會被貼上上一個專案的「台綜大」標籤
- **第一個假設**：KV Cache 記憶洩漏 → 加了 `llama_kv_cache_clear`，**沒有完全好**
- **真正根因**：每次都把全域歷史標籤庫 `existingTags` 塞進 prompt，模型就「參考」了不相關的舊標籤
- **解法**：停止注入 `existingTags`，改成**無狀態、零樣本**推論；再搭配 KV Cache 清除，達成雙層隔離
- **學到的**：**第一個假設不一定對**，要繼續追到真正的根因

### ⭐ 8.2 切換工作區閃退：Workspace Epoch（2026-05-13，`9ea539c`）

- **症狀**：分析途中切換工作區，程式直接 `SIGSEGV`（EXC_BAD_ACCESS）閃退，try/catch 抓不到
- **根因**：對 `QFutureWatcher` 呼叫 `cancel()` 之後，`result()` 指標已經失效，背景任務完成時卻還去讀它
- **解法**：不再暴力取消，改成**樂觀世代控制**
  ```cpp
  std::atomic<uint64_t> m_workspaceEpoch;  // 每次切換工作區就 +1
  // 送出任務時記下 epoch；完成時比對，不一樣就靜默丟掉結果
  if (res.workspaceEpochAtSubmit != m_workspaceEpoch.load()) return;
  ```
- 後來語意搜尋（§3）也用同一套機制

### ⭐ 8.3 macOS 靜默殺程式：OOM（2026-05-13，`65aa862`）

- **症狀**：語意搜尋時程式**沒有任何錯誤訊息就消失**
- **根因**：第一代檢索把 180 筆摘要塞進 prompt，超過 10,000 tokens，Metal 配置 KV Cache 時耗盡統一記憶體，被 macOS 的 Jetsam（OOM Killer）直接殺掉
- **解法**：推論前檢查 `n_ctx - 200`，超過就拒絕；檢索上限改為 30 個檔案
- **後續**：這正是第二代改用 embedding 模型的動機之一 🎯

### 8.4 截斷造成無限生成（Sprint 11.10–11.11）

- **症狀**：UI 和背景 worker 永久卡死
- **根因**：防護網暴力截斷 prompt，連帶切掉 ChatML 的 `<|im_start|>assistant` 標記，模型不知道輪到自己回答，就一直生成下去
- **解法**：超長就直接回傳 `"Error"`，不再盲目截斷；生成迴圈加上硬性上限 `n_predict`（檢索 150、摘要 600）

### 8.5 監控器無窮迴圈（04-30 `75eb75c`、Sprint 13.39–13.40）

- **症狀**：macOS 上批次分析停不下來
- **根因**：寫入 `metadata.json` → 觸發 `QFileSystemWatcher` → 重新掃描 → 又進入分析 → 又寫檔……
- **解法**：Watcher 只負責刷新 UI，**完全和 AI 佇列脫鉤**

### 8.6 單檔分析靜默死亡（Sprint 13.45）

- **症狀**：終端機看得到 PDF 抽取的 log，UI 卻一直沒顯示「分析完成」
- **根因**：共用同一個 `QFutureWatcher`，重複呼叫 `setFuture()`，`finished` 信號因此遺失
- **解法**：每次分析都 `new QFutureWatcher`，用完 `deleteLater()`

### 8.7 無限重跑迴圈：快取有效性標準（Sprint 13.36–13.43）

- **症狀**：已經分析過的檔案一直被重新分析
- **根因**：「怎樣算分析完成」（`hasValidAnalysis`）的標準和 fallback 摘要互相矛盾：fallback 摘要被判定無效 → 重跑 → 又產生 fallback……
- **解法**：最後收斂成「**有 content hash 就算完成**」，摘要品質改由 fallback 文案保證可讀
- **權衡**：可能留下品質差但不會再重跑的摘要（記在 DEVELOPMENT_LOG 的設計權衡）

### 8.8 粉紅大象效應（2026-05-16，`e61f38a`）

- **症狀**：prompt 寫「不要輸出 X」，模型反而更容易輸出 X
- **解法**：不只靠 prompt，在 C++ 端做**硬攔截**（`sanitizeTagsArray`），標籤上限 3 個；後來 GBNF 再從文法層限制數量

### 8.9 Null byte 讓 JSON 崩潰（2026-05-14，`363cf2b`）

- **症狀**：特定 PDF 一分析就崩潰
- **根因**：PDF 抽出的文字夾帶 `\0` 和不可見字元
- **解法**：`sanitizeTextForAi` 淨化管線；GBNF 的 `char` 規則也排除 `\x00-\x1F`

### 8.10 跨執行緒操作 UI 閃退（Sprint 11.7–11.8）

- **根因**：背景執行緒直接修改 `QTreeWidget`（Qt 規定 UI 只能在主執行緒操作）
- **解法**：資料處理放在 `QtConcurrent::run`，UI 更新用 `QMetaObject::invokeMethod` / `QTimer::singleShot` 推回主執行緒

## 9. 分工項目的口試追問與回答

### 🎯 GraphView

**Q：關聯圖譜到底拿來做什麼？只是好看嗎？**
> 「任務是發現跨資料夾的意外關聯。同一個專案的檔案散在三個資料夾，樹狀檔案總管看不出來，圖譜會用共同的分類節點把它們連起來。它的定位是探索，不是日常操作。」

**Q：節點怎麼排？為什麼不會重疊？**
> 「初版用力導向的物理模擬，但資料量一大就會重疊又停不下來。我改成螺旋尋址：每個節點從中心沿著螺旋往外找第一個空位，用 Qt 場景的碰撞查詢加上 20px 邊界，保證不重疊。」

**Q：資料很多時會不會當掉？**
> 「有節點上限，預設 50、可調到 500；而且不是每個小標籤都畫成節點，而是收斂到 18 個分類抽屜。之前沒有上限時真的發生過 OOM。」

### 🎯 GalleryView

**Q：GalleryView 是什麼？在畫面上哪裡？**
> 「GalleryView 是瀏覽層的介面構想，實作成主工作區的四欄結構：標籤樹、資料夾、檔案清單、大型預覽區。清單有三種模式：實體資料夾、虛擬標籤、語意搜尋結果。圖片在預覽區等比縮放顯示。」

**Q：有縮圖牆嗎？**
> 誠實回答：「縮圖格狀牆還沒實作，目前是清單加大型預覽。這是 UI 的未來工作。」

### 🎯 第二個語言模型（語意檢索）

**Q：為什麼要兩個模型？一個不夠嗎？**
> 「聊天模型擅長生成，不擅長比較相似度，而且 context 有限。第一代我們把摘要塞進 prompt 讓它挑，最多只能看 30 個檔案，還發生過 OOM。專用的 embedding 模型只有 440MB，把文字轉成向量後用內積就能比相似度，可以搜整個工作區。」

**Q：向量存在哪裡？檔案改名怎麼辦？**
> 「存在工作區的 `.smartfile/embeddings.bin`，key 是檔案內容的 SHA-256。改名或搬移時內容沒變，向量就不用重算。」

**Q：搜得準嗎？量過嗎？**
> 誠實回答：「分類正確率我們有量化，但搜尋品質還沒做 precision/recall 評測，目前是定性展示。把檢索評測納入 sfo_eval 是下一步。」

**Q：相似度門檻 0.35 怎麼來的？**
> 「是實測後的經驗值；而且前 3 名一定顯示，避免結果空白。比較嚴謹的做法是用標註資料去調這個門檻，這也可以放進評估框架。」

### 跨分工的技術追問

**Q：照片怎麼分析？**
> 見 §5.5：只用 metadata 做保守分類，不讓 AI 假裝看過照片，並標示低信心。OCR 和多模態是未來工作。

**Q：一份 Word 檔怎麼變成 AI 讀得懂的文字？**
> 「docx 其實是 ZIP 壓縮檔。我們用 miniz 在記憶體裡解壓，取出 `word/document.xml`，用 QXmlStreamReader 讀 `<w:t>` 文字節點，再清掉 XML 雜訊、截斷到 1800 字。」
